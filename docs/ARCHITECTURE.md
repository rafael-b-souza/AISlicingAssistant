# Architecture # AI Slicing Assistant — Cura Plugin Technical Notes

Cura Extension plugin: renders photos of the loaded model, sends them plus a stated intent and a whitelisted set of print settings to an OpenAI-compatible chat API, and shows a review table of suggested changes before applying anything to the active profile.

## Architecture

- `SettingsSchema.py` — `CATALOG` (grouped superset of ~45 settings), `DEFAULT_WHITELIST` (~24 enabled by default), `get_enabled_keys()`/`set_enabled_keys()` (persisted via Cura Preferences), `get_setting_scope()` (generic global-vs-per-extruder resolution — never hardcode this per key, ask the live stack via `getProperty(key, "settable_per_extruder")`/`"limit_to_extruder"`), `get_bounds()` (live min/max/type/options via `getProperty()` — **never** parse a `.def.json` file directly, bounds are frequently formula strings resolved against the live stack, e.g. `speed_print`'s max is `sqrt(machine_max_feedrate_x**2 + machine_max_feedrate_y**2)`).
- `SnapshotRig.py` — captures 4-corner + top-down photos by extending `cura/Snapshot.py`'s camera/PreviewPass machinery with a generalized view direction (Cura's own `isometricSnapshot` is left untouched).
- `AIClient.py` — builds the OpenAI-compatible request (`build_system_prompt()` combines fixed safety rules with optional user custom instructions), sends via `UM.TaskManagement.HttpRequestManager` (never a blocking `requests`/`urllib` call inside Cura — freezes the UI thread), and defensively parses the response (`_extract_json_payload` strips `<think>...</think>` reasoning blocks and markdown code fences some models wrap JSON in, and accepts either the requested `{"summary","changes"}` shape or a bare array, since not every "OpenAI-compatible" endpoint honors `response_format` strictly).
- `ApplySettings.py` — the only place that writes to `stack.userChanges`. `validate()` takes the *current* `enabled_keys` explicitly (not a hardcoded constant) and clamps/rejects against live bounds; `apply()` writes only approved + non-rejected changes. Does not trigger a slice itself — that stays a manual step via Cura's own Slice button.
- `AISlicingAssistant.py` — the only file QML talks to. Owns Preferences-backed state: multiple named API profiles (`{name, base_url, model}`, API key stored separately per profile via keyring or a permission-restricted local file), the enabled-keys whitelist, and custom instructions.
- `qml/` — `AIAssistantDialog.qml` (shell: `TabBar`/`StackLayout` + a shared error banner — the banner must live in this file, not inside a tab component, because `Connections.onErrorOccurred` can only reach ids declared in its own file's scope), `AssistantTab.qml`, `ProfilesTab.qml`, `AdvancedTab.qml`, `SuggestionRow.qml`. Files in the same folder become usable QML types automatically (no explicit import needed) — that's how `AssistantTab`/`SuggestionRow` etc. resolve from the main dialog.

## Gotchas already hit (don't reintroduce)

1. **Never manually declare `signal xChanged()` in QML if a `property ... x` already exists.** QML auto-generates that signal; redeclaring it is a "Duplicate signal name" error that silently breaks the whole component (only visible in Cura's log — the UI just does nothing when clicked).
2. **`UM.Dialog` only accepts a single content `Item`.** The i18n catalog, `Connections`, and the main layout all need to live inside one top-level `Item { anchors.fill: parent }`, not as separate children directly under `UM.Dialog` (error: "Cannot assign object to list property 'contents'").
3. **No two-way QML bindings** (`checked: root.checked` + `onCheckedChanged: root.checked = checked`, or reassigning a whole parent object on every child change). This produces "Binding loop detected" warnings and can cascade across every item in a list. Initialize once via `Component.onCompleted`, let `onCheckedChanged` only propagate outward, and mutate shared maps in place rather than reassigning them.
4. **`bool("false")` is `True` in Python** (any non-empty string is truthy). Since AI-suggested values always arrive as strings (see the schema note below), boolean settings need explicit string parsing (`ApplySettings._coerce_bool`), not a bare `bool(value)`.
5. **Not every "OpenAI-compatible" endpoint supports the same JSON Schema features.** Confirmed: MiniMax rejects `response_format.json_schema` union types (`{"type": ["number","string","boolean"]}`) with an HTTP 400 before generating anything. Fix: `RESPONSE_SCHEMA`'s `value` field is a plain `"string"` type (the lowest common denominator), and every value gets coerced to the setting's real type in `ApplySettings.validate()`.
6. **Reasoning models often ignore `response_format` entirely.** Confirmed with MiniMax-M3 (same class as DeepSeek-R1/Qwen-style models): they prepend a `<think>...</think>` block and wrap the actual JSON in a markdown code fence, sometimes as a bare array instead of the requested object shape. `AIClient._extract_json_payload`/`parse_response` handle this generically — don't simplify back to a direct `json.loads()`.
7. **OS keyring may simply not work** (Flatpak sandboxes without D-Bus secrets access, remote/RDP sessions where the login keyring never unlocks). The plugin always tries keyring first and transparently falls back to a local file (`ai_slicing_assistant_apikey_<profile-slug>` in Cura's own data directory, `chmod 600`) — this is intentional, not a bug to "fix" by removing the fallback.

## Development / test loop

No hot reload — Cura must restart to pick up any change.

1. **Test the pure-Python logic first, without Cura.** `SettingsSchema`, `AIClient.parse_response`/`build_request`, and `ApplySettings.validate`/`apply` take plain dicts/dataclasses and can be exercised with a throwaway script using a stub container-stack object (`getProperty(key, prop)` returning canned values) — no Cura/Qt dependency. This is where iteration is fastest; only fall back to a full Cura restart for QML or Qt-integration issues.
2. **Install for manual testing**: symlink (or clone) this folder into `~/.var/app/com.ultimaker.cura/data/cura/<version>/plugins/AISlicingAssistant/` (unbundled plugins live in the user config folder, not Cura's bundled resources — those get overwritten on update).
3. **Restart loop**: kill Cura, delete the old `cura.log` (so the next error is easy to find), relaunch, `grep AISlicingAssistant cura.log` to confirm a clean load before testing anything interactively.
4. **AI prompt/schema iteration**: `AIClient.py`'s `if __name__ == "__main__":` block is a standalone dev harness (plain `urllib`, no Cura/Qt needed) for hitting a real endpoint directly while tuning the system prompt or response schema.
5. **Snapshot framing**: temporarily swap `capture_multi_angle()` for `save_debug_images()` to dump the 5 angles to `/tmp` instead of spending a real API call to check them.

## Marketplace publishing

Package ID `AISlicingAssistant`, SDK version `8.12.0` (Cura 5.13 line — see `plugin.json`'s `supported_sdk_versions`). Submission is via `contribute.ultimaker.com`: zip this folder (root folder name must match the package ID), scan it (VirusTotal), upload via the portal's "Edit release" form. Typical review turnaround is ~2 business days (integration test + human code review). Before zipping: `find . -type d -name __pycache__ -exec rm -rf {} +`.

The Marketplace review policy states packages "should not send user data" — in tension with this plugin's entire purpose. Addressed head-on in `README.md`'s "Data sent to a third party" section: data only goes to the endpoint *the user configures per profile*, never a fixed server of ours, and only on an explicit button click — same posture as already-approved plugins like OctoPrint or Ultimaker's own cloud integrations. If a review ever pushes back on this, that section is the answer, not a code change.
